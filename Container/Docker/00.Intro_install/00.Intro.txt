?? How we build & deploy application(nodeJS) without containers?
    - Install dependencies NodeJS itself needs. ($ apt install nodejs npm)
    - Install nodeJS itself(specific version) to run our javascript files.(nvm install 20)
    - Install application dependencies through package.json. (npm install)
    - Optional build & Compilation - Few language like Typescript(npm run build), Java, Go. Not required for interpretted language like NodeJS
    - Finally, Run our application.(node app.js)

    - We may work on two application one is compatable in node18 and other on node22(nvm use 18). How do we run & manage the different version in same machine?
    - What if manage multiple application running side by side(Go, Java, nodeJS) have conflict with upstream dependencies.( OpenSSL 1.1, libssl-dev, libcrypto.so)
        - Applications dynamically link to these shared libraries at runtime.(libssl.so.1.1, libssl.so.3). They do not overwrite each other.
            - /usr/lib/x86_64-linux-gnu/libssl.so.1.1
            - /usr/lib/x86_64-linux-gnu/libssl.so.3
        - OS upgrade breaks one of them.

?? How do containers come into rescue?
    Container encapsulate all the dependencies and configurations necessary to run whatever applications in whatever language.
    - Simplified Setup: (No need to worry about dependencies) The application with all its specific dependencies, libraries & configurations are bundled into a single image.
    - Consistent environment: No matter how many times you run, it builds with same setup. The container is build with same set of instruction. The immutable image ensures that the environment is identical ehereever the container is run. 
    - isolation: Control over network between containers and host machine are running.
    - High resource Efficiency: More effecient than VM because of shared OS.
    - Best resource control: Fine grain cpu & memory and set limit for containers, so it doesn't consumes resource from other container.
    - Easy Scalable application: Can be rapidly scaled horizontally. 
    - Portability: Same container can run on any machine. All you need is the runtime(docker, containerd,cri-o) installed in the machine that you are running.

?? Containers Vs Virtual Machines:
- Design
    - VM: HW -> Host O/S -> Hypervisor => vm -> GuestOS -> Deps & Code
    - Container: HW -> Host O/S -> Container Engine => container -> Deps & Code
- isolation
    - VM: Strong isolation, Each VM has its own OS, providing complete isolation.
    - Container: Process-level isolation, Container shares the host OS kernel.
- Size/Overhead:
    - VM: Have large footprint because of guest OS and virtual hardware.
    - Container: Lightweight/minimal overhead as they share the kernel with host OS.
- Portability:
    - VM: Less portable because it is tied to specific hypervisor and guest OS configuration and has different format (.vmdk, .vhd, qcow2)
    - Container: High Portable, of platform agnostic and run consistently due t Standard Image Format (OCI) in docker, containerd, CRI-O. 

?? When to use VM?
    - You need strong isolation between different environments.
    - You are dealing with legacy application that might not be easily containerized.
    - You want to reolicate a complete system environment for testing or development.

?? When to use Containers?
    - You are building mordern, cloud-native applications using microservice architecture.
    - You need to scale your application quickly & efficiently.
    - Portability across different environment is a top priority.

?? Docker components:
    - Docker client: Docker CLI(command transformed into API calls), API calls
    - Docker Hosts: Docker daemon(Core Engine, listens for API requests, and also manage conatiners), Rest API(recives request), Containers, Image cache
    - Image Registry: Docker hub(where we retrive the images)

?? Explain the steps Running a container from an image
    - When we issue "docker run" command in docker client, CLI convert the command into relevent api calls and send to docker host.
    - Rest API in docker host recieves the api call and send it to docker daemon.
    - Docker daemon looks for the image in local image cache, if not download from docker hub and stores it in local cache.
    - Then, create a container using the docker image.

?? Explain the steps Building & pushing an image
    - When we issue "docker build" command in docker client, CLI convert the command into relevent api calls and send to docker host.
        - This will include "Dockerfile" & "context"
    - Rest API in docker host recieves the api call and send it to docker daemon.
    - Docker daemon build the image according to the dockerfile and store in local image cache.
    - The image can be tagged locally and pushed to docker hub.
        - Docker CLI send request to docker host. docker host send the image to docker hub.
        - Docker host need to be authenticated to docker registry.

?? Can I can take a container running on a Linux server and run it directly on a Windows server without any issues?
    - Container do not have a guest OS. They shares the kernel of the host OS. A standard linux container cannot run natively on a windows kernel; it requires a compatibility layer(like WSL2) to provide a Linux kernel.
